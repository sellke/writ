# Writ 0.49 Surface Audit and the Case for 1.0

**Date:** 2026-11-09
**Status:** Complete
**Question:** What in Writ 0.49 earns its place, measured, and what should a version built for a semi-technical product manager and current models keep?
**Feeds:** [ADR-034](../decision-records/adr-034-product-manager-audience.md), [ADR-035](../decision-records/adr-035-people-decide-what-model-decides-how.md), [ADR-036](../decision-records/adr-036-plain-language-skills.md), [ADR-037](../decision-records/adr-037-jev-second-reader.md)
**Method:** Three read-only audits of the repository at v0.49.0 (`4692f1a`): the build pipeline, the script and eval surface, and the command surface with usage counted from local session transcripts. pstack re-read at `cursor/plugins` main (2026-10-27 changes). Platform and TypeSafe documentation fetched live on 2026-11-09. Nothing from pstack was executed.

## Answer

Most of Writ 0.49 checked that an agent followed Writ's procedure. Almost none of it checked the product, and the parts that caught real defects were few and simple. Writ 1.0 keeps those parts, states the rest as a short list of principles, and ships as plain-language skills.

## Findings

### 1. Weight (confirmed: counted from files)

| Surface | 0.49 |
|---|---|
| Commands | 34 user-facing, 11,482 lines |
| Agents | 9, 2,262 lines |
| Skills | 19, 2,392 lines |
| Scripts | 98, 56,776 lines |
| Test files | 170, 73,693 lines |
| `eval.sh` | 5,089 lines, 71 checks, 519 literal pins on prose and source |
| Shipped to users | 37 scripts (22,235 lines) and 29 reference docs |

Code and tests outweighed product markdown about 8 to 1. By role: 43 scripts (20,617 lines) only checked Writ's own repository; 19 kept Writ's own artifacts in order; 13 handled install and generation; 8 re-derived an agent's procedural claims; 8 had no live caller; 6 (7% of lines) checked the user's product. Twelve shipped docs were referenced by nothing. Each agent body existed six times in the repository and each command three times, through generated platform trees.

### 2. The build pipeline (confirmed: read from the three implement commands and their records)

The three implement commands prescribed 42 distinct mechanisms.

| Class | Count | Recorded catches of a product defect |
|---|---|---|
| Checks the product (acceptance met, tests pass, app behaves) | 9 | 4 |
| Checks that the agent followed procedure | 16 | 0 |
| Keeps Writ's own artifacts | 8 | n/a |
| Something a current model or harness does unprompted | 9 | n/a |

The four with recorded catches:

- a fresh reviewer checking acceptance criteria against tests it ran (a data-loss defect; an overwrite of user files);
- that reviewer naming the one fact a change is safe because of, and filtering out nits (three valid catches in a four-story trial, labelled by an assistant);
- a pause when the build departs from the contract in a large way (two recorded rejections);
- a check that a test can fail (one fake test blocked).

`implement-story.md` declared ten gates; six read `evidence: none recorded` in its own frontmatter. The Phase 15 retro found agents skipping the prescribed procedure while the procedure checker still returned `met`. Twenty specs across five phase runs produced zero quarantines and zero halts.

The default story path ran 11 scripts. The three commands held 19 ask points, 9 of them about method or failure handling.

### 3. The command surface (confirmed for Claude Code; best effort for Cursor)

Slash-command invocations counted from 355 Claude Code session files and 388 Cursor transcripts, July to November 2026:

- `create-spec` 81, `ship` 56, `implement-spec` 52, `create-issue` 41: 62% of 372.
- Never invoked: `assess-spec`, `edit-spec`, `knowledge`, `migrate`, `refactor`, `revert`, `review`, `security-audit`, `why`.
- Two or fewer: eleven more.
- `/writ`, the front door: 26, all on one date, 17 of them in test folders, none in Cursor.

Across all commands, a hand count found about 100 ask sites, roughly two-thirds about method. Six of 34 command files invoked the rule that was meant to stop method questions.

Limits: the Claude Code window for this repository starts 2026-10-05. Commands reached through routing or called by an orchestrator are not counted. Cursor counts are user messages that begin with the command and undercount chained commands (guess: within 20%).

### 4. Jev as built (confirmed: read from `jev-judge.py` and the calibration report)

`jev-judge.py` was 2,570 lines with 5,491 lines of tests. Its `doubt` site was called for every question a command would ask. No threshold was ever written: on 98 labelled decisions the bound on wrong acts straddled its 10% cap between runs, and scores moved by up to 0.11 on identical input. So `doubt` returned the same answer with or without a provider: ask on direction, design, merge, and release; act otherwise.

The site asked one broad question (is this recommendation right?). TypeSafe's own guidance says to decompose such a question into narrow ones, keep control flow in code, and use the model where a quick, typed judgment over text is needed.

The `spec-findings` site, which asked narrow questions about acceptance criteria, did calibrate: three classes fitted on 24 fixtures with no false positive on clean fixtures in the dev split. On the test split it flagged all three clean stories for a second look.

### 5. pstack since October (confirmed: read from source)

On 2026-10-27 pstack deleted its orchestration scripts and rewrote the Orchestrate playbook as about 25 lines of principle: one owner per unit, a fresh worker per task, a kickoff that names the evidence of done, a verifier who is not the author, a verdict that covers one commit, one unit taken end to end before fan-out, and the user asked only for a real decision. Its text: "Run it with your own tools. Call no scripts, run no polling loops."

pstack still has no planning layer by design. It ships as Agent Skills plus two agent files, with a portable `plugin.json` and a Cursor manifest in one folder.

### 6. Platforms (confirmed: vendor documentation read 2026-11-09; installs not yet exercised)

- All three targets load Agent Skills: a folder holding `SKILL.md` with `name` and `description`.
- Claude Code (terminal and desktop): `.claude/skills/`, or a plugin. Custom commands have been merged into skills. A plugin skill is invoked as `/<plugin>:<skill>`.
- Cursor: `.agents/skills/` and `.cursor/skills/`, and for compatibility `.claude/skills/`. Built-in skills include `/review`, `/loop`, `/autopilot`, `/canvas`, and `/split-to-prs`.
- Codex CLI and the ChatGPT desktop app: `.agents/skills/`, invoked with `$name` or `/skills`; plugins carry a root `plugin.json` and a `skills/` folder, listed in `.agents/plugins/marketplace.json`.
- One plugin folder can carry all three manifests.

## Recommendation

Rebuild to a minimal core: about ten plain-language skills named `writ-*`, one rule for who decides, one independent verifier, a one-file spec, and Jev as an optional second reader of the contract and the proof.

**Strongest case against:** Writ's lead over skill packs was enforcement in code. Removing the scripts gives that up, and a product manager cannot review code to compensate. The answer on record is that the scripts enforced procedure, the verifier is the part that caught defects, and a check comes back only when a recorded miss calls for it. If verified work starts failing in users' hands, this recommendation was wrong.

## Keep, change, avoid, risk

- **Keep:** the contract before code; a verifier that is not the author and runs things; the pause when a build would depart from the contract; plain files in git; honest reporting.
- **Change:** who is asked what (direction only); the spec (one file); packaging (skills); the audience (product managers); Jev's job (second reader).
- **Avoid:** scripts that check procedure; literal pins on prose; per-platform adapters and generated trees; a second copy of anything.
- **Risk:** a weak verifier with nothing behind it; no product manager has used Writ yet; existing 0.x projects need the old uninstaller before the new install.
