## Specification Contract

**Deliverable:** `/why "<question>"` answers why something in this project is the way it is. It reads Writ's ledger first, then git history, then connected MCP servers. Every claim carries one of five confidence tiers. When a change follows, the answer ends with a `## Preserve / Change / Avoid / Risk` section, saved under `.writ/research/`, and `/create-spec` discovery reads that section.

**Must Include:**

1. **Source order.** The ledger first: `refs/notes/writ` notes on the anchor commits, specs (archived ones included) with their drift logs and What Was Built records, ADRs, the knowledge ledger, and issues. Then git history: commit messages, merge commits, and the PR and issue numbers they cite. Then MCP servers already connected in the session and the code host's CLI, only when the ledger and git leave the strongest claim below `Stated`.
2. **Five confidence tiers** on every claim: `Recorded`, `Stated`, `Corroborated`, `Inferred`, `Unknown`. Code is never evidence of its own intent. A null result names the sources searched.
3. **One fixed handoff shape.** The heading `## Preserve / Change / Avoid / Risk` with `### Preserve`, `### Change`, `### Avoid`, `### Risk` beneath it, in that order. Each item names its tier and source. The answer and the section are saved to `.writ/research/<YYYY-MM-DD>-why-<slug>.md` with a header carrying `Asked`, `Subject`, `Change`, and `Question` lines.
4. **`/create-spec` reads the handoff.** A new Step 1.2 in `commands/create-spec.md` finds the section in the conversation, in a file the invocation names, or in a `.writ/research/*-why-*.md` record whose `Subject` or `Change` line shares a keyword with the feature idea, and carries the four lists into the contract.
5. **The front door routes to `/why`.** The why-or-how row in `commands/writ.md` routes to `/why`. A question about something outside the project (a library, a standard, a vendor) stays on `/research`. The prompting guide's route line follows.
6. **Registration** on every catalog surface. Generated files are regenerated by their generators, never hand-edited.
7. **`entry_level: high`.** The command renders an unverified judgment the user acts on.

**Hardest Constraint:** Answer from the cheapest sufficient evidence without overstating confidence. `/why` reads the ledger before git and git before any MCP server, spawns no subagents, and stops sweeping once a `Recorded` claim stands and later history does not contradict it. pstack's seven-source sweep is declined by default (ADR-030, ADR-023).

**Success Criteria:** `commands/why.md` passes `check_command_structure`, `check_referenced_paths`, and the vendor scan, and stays under the 24,960-byte command budget. A test pins the five tiers, the source order, the fixed heading in both `commands/why.md` and `commands/create-spec.md`, the `/why` route in `commands/writ.md`, and every registration surface. The dogfood fixture (technical-spec.md → Dogfood Fixture) answers four questions about Writ's own history at the expected tier, and `/create-spec` Steps 1.1–1.2 carry the saved record's four lists into a draft contract. `uv run --python 3.9 pytest`, the bash tests, and `bash scripts/eval.sh` report 0 failures and 0 findings.

**Scope Boundaries:**

- Included: `commands/why.md`; `/create-spec` Step 1.2; the `/writ` route row and its Step 2 bullet; the prompting guide's route line; registration, generated trees, and the tests that pin them.
- Excluded: always-on multi-model panels; cross-vendor routing (ADR-024 stands); formal verification; one investigator subagent per source; writing git notes or editing any ledger entry; a `--recommend` flag on `/why`; an adapter row for MCP discovery; a helper script; reading the handoff in `--from-issue` or `--from-prototype` mode.

## 🎯 Experience Design

### Entry Point

- `/why "why does the importer skip rows with empty emails?"`
- `/why src/billing/invoice.py:120` asks why that code is the way it is.
- `/writ "why is X like this?"` routes here after its one confirmation.

### Happy Path

1. Anchor: `/why` restates the question in one line, finds the files and symbols it names, and lists the commits that introduced or last changed them.
2. Ledger: it reads the `refs/notes/writ` notes on those commits, the specs and drift logs they name, the ADRs and knowledge entries that mention the subject, and the What Was Built records.
3. Git: it reads the commit messages and merge commits, and checks whether anything changed after the ledger entry.
4. Answer: one or two sentences with a tier, a claims table, and the sources searched.
5. When a change follows: the `## Preserve / Change / Avoid / Risk` section, saved to `.writ/research/`, and the next step: `/create-spec`.

### Moment of Truth

The answer quotes the ADR, spec rule, or DEV entry that made the decision, with its path, before the user changes the code.

### Feedback Model

- The answer's first line names the strongest tier reached.
- The Sources searched list shows what was read, in source order, and where nothing was found.
- A saved record prints its path and the `/create-spec` line that reads it.

### Error Experience

- The subject cannot be found: `/why` says what it searched for and asks one natural-language question about where it lives. No menu.
- No ledger in the project: the answer says so and reads git history.
- Not a git repository: the answer says so and reads the ledger by path only.
- Neither source exists: the answer is `Unknown` and names what was searched.
- An MCP call fails: the answer names the server and reason under Sources searched and continues without it.

### State Catalog

| State | What the user sees |
|---|---|
| Ledger states the reason | Answer at `Recorded`, quoting the entry and its path |
| Only a commit message states it | Answer at `Stated`, citing the commit SHA |
| Two sources point to it, none states it | Answer at `Corroborated`, both cited |
| One source suggests it | Answer at `Inferred`, the source cited |
| Nothing found | Answer at `Unknown`, with the sources searched |
| Ledger and later history disagree | Both shown, the newer one named, the claim at the lower tier |
| Code changed after the ledger entry | The claim keeps its tier, and a line says the entry may describe an earlier shape |
| A change follows | The section and the saved record path |
| No change follows | The answer only; nothing is written |
| Subject not found | One natural-language question; no answer yet |

### Output Shape

The answer prints a `## Why: <subject>` heading, an `**Answer:**` line ending in its tier, a `### Claims` table (`#`, `Claim`, `Tier`, `Evidence`), and a `### Sources searched` list with `Ledger`, `Git`, and `MCP` lines in that order. The saved record adds the header lines and ends with the handoff section. technical-spec.md → Output Templates holds the literal templates.

## 📋 Business Rules

1. **Ledger first.** Read sources in this order: the ledger, git history, then MCP servers and the code host's CLI. The Sources searched list follows the same order.
2. **The anchor locates.** `git blame`, `git log -L`, and `git log --follow` find the commits that touched the subject. They point at evidence; a commit's existence is not evidence of why.
3. **Five tiers.** `Recorded`: a ledger entry states the reason. `Stated`: a person wrote the reason at the time outside the ledger, in a commit message, a PR or issue, a chat thread, or a code comment written in the same commit as the code. `Corroborated`: no source states it, and two or more independent sources point to it. `Inferred`: one source suggests it. `Unknown`: no source found.
4. **Code is not evidence of its own intent.** The shape of the code shows what it does, never why. A claim resting only on the code is `Unknown`.
5. **Null results are reported.** Every source read that held nothing on the subject is named under Sources searched.
6. **Conflicts take the lower tier.** When sources disagree, show both, say which is newer, and give the claim the lower of the two tiers. A newer ledger entry that says it supersedes the older one settles the conflict at its own tier.
7. **MCP only when needed.** Read MCP servers and the code host's CLI only when the strongest claim after the ledger and git is below `Stated`. Use only servers already connected. Never ask to connect, install, or authorize one.
8. **Read-only.** `/why` writes no git ref, note, or commit, edits no ledger entry, and makes only read calls to MCP servers. Its one write is the saved record.
9. **No subagents.** `/why` runs in the session that invoked it.
10. **A change follows** when the request names a planned change, or the user names one after the answer. Without one, `/why` answers and writes nothing.
11. **Fixed handoff shape.** The heading reads exactly `## Preserve / Change / Avoid / Risk` and is the last `##` section of the saved record. Its four `###` subsections appear in the order Preserve, Change, Avoid, Risk. Each item ends with its tier and source. An empty subsection reads `- none found`.
12. **Saved record.** Path `.writ/research/<YYYY-MM-DD>-why-<slug>.md`, slug kebab-case from the subject, at most six words. An existing path gets `-2`, `-3`, and so on; `/why` never overwrites a record.
13. **The handoff maps into the contract.** `/create-spec` Step 1.2 carries Preserve into Business Rules, Change into the Deliverable, Avoid into Scope Boundaries → Excluded, and Risk into Technical Concerns. Each carried item keeps its tier and cites the record. Discovery does not re-ask what the section settles.
14. **Front-door route.** The `commands/writ.md` routing row for why-or-how questions routes to `/why`, and the same cell names `/research` for questions about something outside the project. The table keeps six rows.
15. **Generated files are regenerated.** `SKILL.md` by `bash scripts/gen-skill.sh`; `claude-code/CLAUDE.md`, `codex/AGENTS.md.template`, `cursor/plugin/`, and `plugins/writ/` by `python3 scripts/gen-platform-trees.py`. Every story that edits a `commands/*.md` file regenerates.
16. **Budgets.** `commands/why.md` stays under 200 lines and under the 24,960-byte command budget. Step 1.2 adds under 700 bytes to `commands/create-spec.md`. Tests use the Python 3.9 standard library.
17. **Entry level.** `entry_level: high` by Q1 of the two-question derivation: the command renders an unverified judgment the user acts on.

## Implementation Approach

- **Order.** Story 1, then Story 2. Stories 3 and 4 both need Story 2 and touch different files, so they can run in one batch. Story 4 also needs Story 1's heading.
- **Thin command.** `commands/why.md` targets under 200 lines, the size of `commands/writ.md` and `commands/research.md`. If it grows past that, investigation machinery is leaking in.
- **Subtraction.** The interim text in `commands/writ.md` ("`/why` takes this route when it ships") and the prompting guide ("`/why` replaces it when it ships") is removed, per Design Principle 7. No other surface could be removed: `/research` keeps its external-question route.
- **Prose.** Read `skills/plain-prose/SKILL.md` before writing any command prose. Grep `scripts/` for a fragment of every sentence changed in `commands/writ.md` and `commands/create-spec.md` before rewording it.
- **Edits by heading.** Locate every edit by section heading or list text, never by line number.
- **Verification.** `uv run --python 3.9 pytest`, then `for t in scripts/tests/test_*.sh; do bash "$t" || echo "FAIL $t"; done`, then `bash scripts/eval.sh` outside any sandbox, after every story. Run pytest alone, never beside eval or the bash tests in the same tree.
