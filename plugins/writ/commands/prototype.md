# Prototype Command (prototype)

## Overview

The early workflow for an idea that needs **looking at** before it needs specifying. Describe it, see a few genuinely different takes, pick one, and ship it with TDD and lint verification. No spec files, no multi-gate ceremony, no pre-flight questions.

Two things end a `/writ:prototype` run, and both are success:

- **A direction chosen.** Several code-portable drafts existed, one won, and the reasons the others lost are recorded. No code need be written.
- **A change shipped.** The work was small enough to just build, with tests and lint.

Most runs end in both. A run that produces three drafts, a decision, and no code is finished, not abandoned.

Use `/writ:prototype` when the cost of a specification exceeds the value of the change, or when the direction is not settled enough to specify. For anything that touches core architecture, needs cross-team coordination, or spans many files, use `/writ:create-spec` + `/writ:implement-story` instead.

**What this command will not do:** deep specification, story decomposition, task lists, or planning artifacts. It gets you a real sense of the end in mind and stops there. `/writ:create-spec --from-prototype` is the door to the rest.

**How it differs from `--quick` mode on `/writ:implement-story`:**

| | `/writ:prototype` | `/writ:implement-story --quick` |
|---|---|---|
| **Spec required?** | No — operates without any spec | Yes — requires an existing story file |
| **Input** | Description (inline, attached file, or conversation context) | Story file with tasks and acceptance criteria |
| **Pipeline** | Scan → [Diverge → Choose] → Code → Lint → Done | Code → Lint → Test (skips arch-check, review, docs) |
| **Best for** | Unsettled ideas, ad-hoc changes, bug fixes, small features | Prototyping a specific story within a larger spec |

## Invocation

| Invocation | Behavior |
|---|---|
| `/writ:prototype` | Uses conversation context — attached files, preceding messages, or user's description |
| `/writ:prototype "description"` | Explicit inline description |
| `/writ:prototype @issue-file.md` | Reads the attached issue/file as the change description |
| `/writ:prototype --diverge "..."` | Forces Step 2.5 on — draft the idea before building anything |
| `/writ:prototype --no-diverge "..."` | Forces Step 2.5 off — build the obvious shape |

All invocations go straight to Context Scan with no interactive questions. If the input is ambiguous, ask a single clarifying question in natural language rather than presenting a menu.

## Command Process

### Step 1: Extract Intent

Parse the change description from the user's input:

1. **Inline text** — `/writ:prototype "fix pagination off-by-one"`
2. **Attached file** — `/writ:prototype @issue-file.md` (read for description, files, constraints)
3. **Conversation context** — `/writ:prototype` with preceding messages
4. **Bare invocation** — no context → ask: "What do you want to build or change?"

Extract: **what** to change, **where** (file hints for context scan), and **watch-outs** (constraints, compatibility, design notes). Issue files typically contain all three; one-liners rely on the context scan to discover the rest.

### Step 2: Context Scan

Gather lightweight context before coding:

1. **Read the target area** — files from the description plus their surrounding module
2. **Detect tech stack** — language, framework, test runner, linter config
3. **Find related patterns** — similar implementations to guide the approach
4. **Check test conventions** — test file locations and naming patterns
5. **Discover scope** — which files need modification
6. **Sniff nearby rules** — scan for permission checks, validation logic, state machines, or business rules the change must respect. Pass discovered rules to the coding agent.
7. **Detect UI surface** — classify as UI-touching (one of the two Step 2.5 gates)

**UI detection heuristic:** UI-touching if any of:
- Files match frontend patterns: `*.tsx`, `*.jsx`, `*.vue`, `*.svelte`, `*.html`
- Target area includes: `components/`, `pages/`, `app/`, `views/`, `layouts/`, `screens/`
- Description contains visual language: "button", "modal", "layout", "form", "page", "dashboard", "sidebar", "card", "table", "nav", "header", "footer", "responsive", "style", "CSS", "UI", "design"

**Figma MCP detection:** if the `canvas-preview` capability (see the adapter) and `design-system.md` or a Figma MCP server are available, note in context so the coding agent generates token-referenced code instead of hardcoded values.

Output a brief context summary (internal: passed to the coding agent, not shown to the user):

```
Context:
- Tech: TypeScript, Next.js, Jest, ESLint + Prettier
- Target area: src/components/settings/
- Related patterns: existing toggle components use `useLocalStorage` hook
- Test location: __tests__/components/settings/
- Files to modify: [list]
- Nearby rules: [e.g., "requireAuth middleware on this route", or "none found"]
- UI change: true
- Direction settled: false — description names a goal, not a change
- Design tokens: .writ/docs/design-system.md (loaded)
- Component vocabulary: [names the drafts and the coding agent must both use]
```

### Step 2.5: Diverge & Choose

**Gated — most runs skip this.** Run it when the change touches UI (Step 2's
detection) **or** when the direction is unsettled: the description names a goal
rather than a change, the input is an issue file with an open "Expected Outcome",
or the user asked for options. A bug fix with one obvious shape skips straight
to Step 3, exactly as it does today. `--diverge` forces it on; `--no-diverge`
forces it off.

#### What a draft is

A **rendered, self-contained page** built from the project's own component names,
CSS framework, and design tokens. Structurally accurate, not pixel-polished.
Placeholder copy is fine; invented components are not.

A draft is **not** a screenshot, **not** an abstract wireframe, and **not**
running application code. Drafts are render-only — the point is to look at the
idea cheaply, not to build it three times.

> **The portability test:** a coding agent reading the draft can name the
> components to create or change without guessing. If it cannot, the draft is a
> picture, and a picture is not worth keeping. Label every region with the
> component it maps to.

#### Getting drafts that actually differ

`Read ${CLAUDE_PLUGIN_ROOT}/skills/design-divergence/SKILL.md` for how to get drafts that differ: axes
declared first, one context per draft, a commitment before rendering, ordinary
personas. This step owns when drafts are made, what a draft is, how they render,
and the record. Default to three drafts.

#### Render through the platform

Writ ships no renderer. Use what the platform provides, best available first:

| Available | Use |
|---|---|
| Native artboard/design surface | Platform's own canvas; point it at the project's components so it does not re-draw what exists |
| `canvas-preview` (the adapter maps it) | A self-contained HTML page per draft, project framework and tokens |
| Neither | A written structural description per draft — say plainly that drafts were not rendered |

Each adapter maps `canvas-preview` to its own tool and states what to do when it has none. Never degrade silently.

#### Present and choose

Show the drafts together with their axis commitments, not one at a time —
comparison is the whole point. Then:

```
🎨 Three takes on [idea]
  A — [axis combination] · [the trade-off it accepts]
  B — [axis combination] · [the trade-off it accepts]
  C — [axis combination] · [the trade-off it accepts]

Pick one to build, ask for a fourth on a different axis, or stop here with the decision recorded.
```

**Record the decision.** Write `.writ/prototypes/<date>-<slug>/exploration.md`: the
axes, one row per draft, the chosen draft, and **why each rejected draft lost**.
Keep the rendered drafts beside it. The rejected alternatives are the durable
part — they are the "what else did we consider" that `/writ:create-spec --from-prototype`
carries into the spec contract, and the thing nobody can reconstruct six months on.

This is an exploration record, not a spec. It creates nothing under `.writ/specs/`.

**If the user stops here, the run is complete.** Report the decision and offer
`/writ:create-spec --from-prototype` for later. Do not build unasked.

### Step 3: Spawn Coding Agent

> **Agent:** `${CLAUDE_PLUGIN_ROOT}/agents/coding-agent.md` (prototype mode)
>
> **Sub-agent worktree integration:** `Read ${CLAUDE_PLUGIN_ROOT}/skills/subagent-worktree-integration/SKILL.md`

Spawn the coding agent with extracted intent and codebase context.

The change is done only when it is in the user's checkout. When the agent's result names a worktree path or a branch other than the current one, integrate it as the skill describes before Step 4, writing no temporary file outside the project (pipe the worktree's diff into `git apply`), then confirm with `git status` that the changed files are in this checkout.

**Required context to include in prompt:**
- Change description and watch-outs
- Full context scan output (tech stack, patterns, nearby rules, files to modify)
- The chosen draft and its axis commitment if Step 2.5 ran — the agent builds that direction, not a fresh interpretation
- Design tokens reference if available

**Principles to instruct:**

1. **TDD** — tests first covering core behavior and obvious edge cases
2. **Match codebase** — follow existing patterns and conventions
3. **Respect nearby rules** — don't bypass auth, skip validation, or ignore state transitions.
4. **Don't ship only the happy path** — handle error, empty, and loading states.
5. **Keep focused** — prototype scope, not full feature build
6. **Build the chosen draft** — if Step 2.5 ran, match its layout and component hierarchy, and reuse the component names it labelled. The draft was built to port; port it.

**Scope escalation signals:** instruct the agent to flag if any are true:

- More than 5 files need creation or modification
- New database schema changes or migrations are required
- The change touches core architecture, shared utilities, or base classes
- Test coverage in the affected area is already low (<50%)
- The change depends on other incomplete or in-flight work
- New external dependencies need to be added

If flags trigger, complete the implementation but include a scope escalation notice.

### Step 4: Lint & Typecheck

Auto-detect and run project linters and typecheckers. The AI infers tool selection from the project's config files.

**On failure:** auto-fix what's fixable (formatter, auto-fixable lint rules) → re-run → still failing → send to coding agent for one fix attempt → still failing → report remaining issues in summary.

## When to Use /writ:prototype vs Other Commands

| Scenario | Use |
|---|---|
| Quick bug fix | `/writ:prototype "fix off-by-one in pagination"` |
| Add a utility function | `/writ:prototype "add string truncation helper"` |
| Small UI tweak | `/writ:prototype "add loading spinner to save button"` |
| Bug with issue file | `/writ:prototype @issue-file.md` |
| Unsettled idea — want to see a few takes first | `/writ:prototype "a way to review flagged items in bulk"` |
| Exploring an approach before committing | `/writ:prototype` (then escalate if it works out) |
| Multi-file feature with dependencies | `/writ:create-spec` + `/writ:implement-story` |
| Refactoring a specific file | `/writ:refactor` |
| Mockups for a spec that already exists | `/writ:writ-design` |
| Change within an existing spec | `/writ:implement-story --quick` |

## Completion

This command succeeds when the idea is in front of the user as something real, and no spec artifact was written for it. That is either:

- **A direction chosen** — code-portable drafts existed, one won, and `exploration.md` records the choice and why each rejected draft lost. No code is required.
- **A change shipped** — it sits in the working tree with tests written first and the linter and typechecker run.

Most runs are both. A run that ends at a chosen direction is complete, and must be reported as complete rather than as work left over.

A scope-escalation signal firing is also a valid outcome, not a failure. It is named in the summary alongside the `/writ:create-spec --from-prototype` offer, and the decision belongs to the user.

**Terminal constraint:** This command explores an idea and ships small changes. Do not write spec artifacts, decompose stories, open a PR, or escalate to the story pipeline without an explicit yes. Deep specification is `/writ:create-spec`; drafts for a spec that already exists are `/writ:writ-design`.
