# Retro Command (retro)

## Overview

`/writ:retro` reads the transcripts of an implementation run and finds where the agent struggled. It then proposes changes to the agent's environment so the next run does not struggle the same way. It does not touch source code.

Run it after `/writ:implement-story`, `/writ:implement-spec`, or `/writ:implement-phase`, or point it at any session. It works in the Writ repo, where findings improve Writ itself, and in any project using Writ, where findings improve that project's setup.

**Principles:**

- **Fix the environment, not the code.** Targets are steering files, navigation hints, lint and architecture rules, skills, docs, and ignore files.
- **Fix at the highest rung that works.** Architecture, then types, then a lint, then a test, then docs.
- **Evidence or it does not count.** Every finding cites a transcript path and a short observable signal. A suspicion without a citation is not reported.
- **Most severe first.** A hidden false green outranks a slow file search.
- **The human decides.** The command proposes; nothing is applied without approval.
- **Transcripts stay out of the repo.** Only paths and short factual quotes are stored.

## Invocation

| Invocation | Behavior |
|---|---|
| `/writ:retro` | Most recent completed implementation run, detected from `.writ/`; asks if none is found |
| `/writ:retro --story <spec-path> <n>` | One story |
| `/writ:retro --spec <spec-path>` | One spec, all its stories |
| `/writ:retro --phase <phase-id>` | One phase, all its specs |
| `/writ:retro --session <path-or-uuid>` | Named transcripts, including an ongoing session or work outside the Writ pipeline |
| `/writ:retro --since <N>d` | Every session for this project in the last N days |
| `/writ:retro --report-only` | Findings and the retro file, no apply step |

## Command Process

### Step 1: Resolve Scope

Turn the scope into a time window, a set of branches, and a set of working directories. Transcripts are selected by these three.

| Scope | Window | Directories |
|---|---|---|
| Story | first to last commit recorded in the story file, padded 30 minutes before the first | repo root plus the story's worktree, if any |
| Spec | `spec.md` created date to completion date, or now if in progress | repo root plus every worktree in `git worktree list` used for the spec |
| Phase | start and end recorded in `.writ/state/phase-execution-*.json` for that phase | repo root plus every lane worktree |
| Session | the session's own first and last timestamps | as recorded in the transcript |
| `--since` | now minus N days to now | repo root plus all current worktrees |

If a scope path does not exist, list what does (`.writ/specs/`, phase ids) and ask. If `.writ/` is absent, only `--session` and `--since` are available; say so.

### Step 2: Locate Transcripts

| Platform | Location | Useful fields |
|---|---|---|
| Claude Code | `~/.claude/projects/<repo path with / replaced by ->/<session-uuid>.jsonl`; subagents in `<session-uuid>/subagents/agent-*.jsonl` | per-line `timestamp`, `cwd`, `gitBranch`, tool calls and results, `message.usage` token counts |
| Cursor | `~/.cursor/projects/<project-slug>/agent-transcripts/<session-uuid>/<session-uuid>.jsonl`; subagents under `.../subagents/<sub-uuid>.jsonl` | messages and tool calls |
| Codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` | per-line timestamps, `cwd`, tool calls |
| Other | ask the user for a path | whatever the format carries |

Keep sessions whose timestamps overlap the window and whose working directory is one of the scope's directories. Include subagent transcripts of kept sessions. An ongoing session is allowed; mark its findings partial.

If no transcripts are found, print where you looked and offer `--session <path>`.

**Reading large transcripts.** Do not read transcripts end to end into the main context. Extract a compact event list per session: timestamp, tool name, target path or command, success or error, user messages, and token usage where present. With more than three sessions, analyze each in a parallel subagent that returns findings in the Step 5 shape and nothing else.

### Step 3: Detect Struggle Signals

Look for these patterns in the event lists. Report a pattern only when the transcript shows it.

| Signal | What the transcript shows | Typical environment fix |
|---|---|---|
| **Silent patch** | a failure worked around without saying so in the final report: test skipped or deleted, check disabled, retried until green, error swallowed | a gate or lint that makes the workaround visible; a steering rule forbidding it |
| **Stale guidance** | the agent followed a doc, rule, or command step, then hit an error or a user correction showing the guidance was wrong | update or delete the doc; add an eval or lint that keeps it true |
| **Repeated mistake** | the same error class fixed twice or more in scope, or a finding that recurs from an earlier retro | a lint rule, architecture rule, test, or hook that fails fast |
| **User correction** | the user corrected, overrode, or re-explained something the agent should have known | the rule or doc line that would have prevented it |
| **Dead end** | an approach abandoned: edits reverted, files created then deleted, a long tool sequence ending in a different plan | record the constraint where the agent will read it: steering file or `/writ:knowledge` lesson |
| **Navigation churn** | many search, list, or read calls before the first edit of the file that was changed; searches for names that do not exist; the same file read repeatedly | a path map or navigation hint in the steering file; an ignore entry; a rename |
| **Duplicated work** | two agents or stories derive the same context; the same subagent spawned twice for one job; the same large file re-read across gates | a shared context file, a skill, or a story-context hint |
| **Token sink** | turns with very large input or tool output for little progress, from `message.usage` or output size; long wall-clock gaps between tool calls | ignore patterns, smaller or split docs, output caps on noisy commands |
| **Writ command defect** | a Writ command step confused the agent, was skipped, or failed | `/writ:refresh-command <command>`, or an Improvement Request upstream |

Count occurrences. Three occurrences make a pattern (ADR-014). A single silent patch or stale-guidance event counts on its own. A user correction or mistake against a rule whose enforcer is `none` in the rule table counts on its own, as a Repeated mistake. Keep single corrections and mistakes until Step 4 has read the table.

### Step 4: Rank by Severity

Before ranking, read `.writ/retros/rule-enforcers.md` if it exists. If it does not, say no rules are tabled yet. Match a finding to a row by rule and target.

| Severity | Criteria |
|---|---|
| **Critical** | hid a defect or produced a false green: silent patch, disabled check, wrong output that shipped |
| **High** | repeated mistake, stale guidance that sent the agent wrong, user correction |
| **Medium** | dead end, navigation churn, or duplicated work that cost many turns or tokens |
| **Low** | a one-off inefficiency |

Within a severity, order by cost: turns, then tokens, then wall-clock time.

Read earlier files in `.writ/retros/`. When a finding matches an earlier one by signal and target, and the earlier one was `applied`, raise it one level and mark it **fix did not hold**. When it matches an earlier `deferred` or `dismissed` one, say so. When a finding's mistake breaks a rule the table lists with an enforcer, raise it one level, mark it **enforcer did not hold**, and name the row, even for a single event. When the row's enforcer is `none`, say so; the finding's ladder proposes an enforcer. Drop single user corrections and mistakes that match no row.

Report the top 10. Give the count of the rest and list them in the retro file.

### Step 5: Propose Environment Changes

Each finding uses this shape. The Evidence block matches `/writ:refresh-command`'s, so a finding can be handed to it unchanged. The example shows a finding after Step 6 ran its proof.

```markdown
### F1 [High] Repeated mistake: bare except hides errors
**Evidence:**
- Transcript: ~/.claude/projects/<repo-slug>/<session-uuid>.jsonl
- Observable signal: a bare `except:` replaced with a named exception after review (3 times)
- Cost: 3 turns, about 40k input tokens
**Rule:** catch a named exception, never a bare `except:`
**Rung:** lint
**Ladder:** architecture: no (not a module boundary); types: no (a type checker does not flag it); lint: yes
**Target:** ruff.toml → [lint] select
**Change:** (diff adding "E722")
**Proof:** mistake 3f2c1ab; check `ruff check src/`; result fails
**Route:** apply
```

**Routes:**

| Route | When |
|---|---|
| `apply` | target is a project environment file: `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/*`, `.writ/docs/*`, ignore files, lint, type-checker, or architecture rule config, `skills/*/SKILL.md`, project docs |
| `refresh` | target is a Writ command or agent file; hand off to `/writ:refresh-command <name>` with the Evidence block |
| `issue` | the fix needs design work (a script, a schema, a new gate) or a source or test edit: draft it for `/writ:create-issue`. A source or test edit carries the finding's proof as the issue's done check. In a project using Writ where the defect is in Writ itself, draft an Improvement Request and send it only on explicit confirmation |
| `knowledge` | the finding is a durable fact or lesson; hand off to `/writ:knowledge` |

Never target source code or tests. If the fix is unclear, write the open question as the change instead of guessing.

### Fix ladder

Silent patch, Stale guidance, Repeated mistake, and User correction findings take the first rung in this table that would have stopped the mistake. Other findings carry `**Rung:** none` unless a check would prevent them; then they follow the same rules.

| Rung | What it is in /writ:retro | Route |
|---|---|---|
| architecture | a ruleset `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/arch-lint.py detect` finds (see `.writ/docs/architecture-lint.md`), or a boundary or layout rule | `apply` when config-only; `issue` otherwise |
| types | a type-checker setting | `apply` when config-only; `issue` otherwise |
| lint | a lint rule whose message names the fix | `apply` when config-only; `issue` otherwise |
| test | a test that fails on the mistake | `issue`; never `applied` |
| docs | a steering file, doc, skill, command, or `/writ:knowledge` entry | `apply`, `refresh`, or `knowledge`, as in the routes above |

**Ladder line.** `**Ladder:** <rung>: no (<reason>); ...; <rung>: yes`. Start at architecture and list each rung in order, with no gaps, down to the chosen one. Give every `no` a reason in parentheses. End with the one `yes`; its rung is the Rung line.

**Proof line.** A finding at architecture, types, lint, or test carries ``**Proof:** mistake <ref>; check `<command>`; result <fails|passes|pending>``. `<ref>` is a commit SHA in this repository that holds the mistake, or a transcript path exactly as listed under `## Transcripts` in the retro file. A fixture written for the occasion is not a past mistake. Materialize the mistake without touching the working tree: `git show <sha>:<path>` into a temp directory, or `git worktree add --detach <tmp> <sha>` when the check needs the whole tree, removed afterwards. For a transcript ref, rebuild the snippet the transcript quotes in a temp file. Run the check with the new config against it. The result is `pending` until Step 6 runs the proof, and `applied` requires `result fails`. Docs-rung findings need no proof.

### Step 6: Review with the Human

Skip this step with `--report-only`.

Present the ranked findings. For each, use `AskQuestion` with these options, labelling the finding's route as `(Recommended)`:

- **Apply** — edit the target file and show the diff
- **Hand to /writ:refresh-command** — for command and agent targets
- **File an issue** — draft only; the user runs `/writ:create-issue` or confirms the send
- **Dismiss** — with an optional one-line reason
- **Defer** — keep for the next retro

When two findings name the same rule, offer Apply on the first only. Record the second as `dismissed` with the reason `same rule as F<n>`; it gets no table row.

Apply only approved changes. Each applied edit follows `${CLAUDE_PLUGIN_ROOT}/skills/plain-prose/SKILL.md`. Leave the edits as a reviewable diff; this command does not commit.

**Proof run.** After an Apply on architecture, types, or lint, run the finding's proof (Step 5):

- The check fails on the mistake: keep the edit, set `result fails`, and record `applied`.
- The check does not fail: restore the file to its pre-edit content, set `result passes`, record `issue`, and say the check passed on the past mistake.
- The check cannot run, because the tool is missing or the mistake cannot be materialized: set `result pending` and record `issue`. The issue draft carries the proof command as its done check.

### Step 7: Read-only Nudges

These two checks are read-only. They may print one line each and never block the retro.

**Knowledge consolidation.** Skip silently when `.writ/knowledge/` is absent or empty. Otherwise run the dry-run reducer, which writes nothing:

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/knowledge-consolidate.py --json
```

If it reports any `merges`, `contradictions`, or `stale` findings, or the ledger holds more than about 20 entries, print: *"Knowledge ledger has pending consolidation candidates — consider running `/writ:knowledge --consolidate`."* This step mutates no knowledge file and never runs consolidation itself.

**Product drift.** Skip silently when `.writ/product/` is absent. Otherwise compare phase status labels in `mission.md` and `roadmap.md` in both directions (same test as `/writ:verify-spec` Check P1). When they disagree, print one line naming the phase and which side is ahead, and suggest `/writ:verify-spec --product` or `/writ:plan-product --reconcile`. This step mutates no product file.

### Step 8: Persist the Retro File

Write `.writ/retros/YYYY-MM-DD-<scope-slug>.md`, creating the directory if needed:

- Scope, window, branches, and directories
- `## Transcripts`: one list item per transcript read, its `~`-relative path in backticks first, then the partial flag where it applies
- Counts per signal and per severity
- `## Findings`: every finding in the Step 5 shape under its `### F<n> [<Severity>] <Signal>: <title>` heading, with a `**Rung:**` line (`none` outside the ladder) and a `**Disposition:**` line holding only `applied`, `refreshed`, `issue`, `dismissed`, or `deferred` (`deferred` for all findings under `--report-only`); a dismissal's reason goes on a `**Reason:**` line
- For **fix did not hold** findings, the earlier retro file and finding id; for **enforcer did not hold** findings, the table row
- `## Rule table changes`: each row this run added or replaced, or `none`

**Rule table.** For each `applied` or `refreshed` finding whose rung is not `none`, replace the rule's row in `.writ/retros/rule-enforcers.md` if it has one; otherwise add a row. If the file does not exist, create it with the heading `# Rule-to-Enforcer Table` and the header row `| Rule | Written in | Enforcer | Rung | Proof | Since |`. Since is `<retro file name> F<n>`, for example `2026-10-29-spec-x.md F1`. A docs-rung row has Enforcer `none` and Proof `—`. Any other row names the check command or config path in backticks as Enforcer, with Proof `<ref>: fails`. Under `--report-only`, the table does not change.

**Check the record.** Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/retro-check.py --retro <file>`. On `fail`, correct the retro file, or the rows this run added or replaced, where each reason line points, and run it once more. A proof result changes only by running the proof again. Put a second `fail`, or an `unverifiable` verdict, in the final report with its reason lines. The environment edits stay.

Commit this file with the project's next commit; it is the history the next retro reads. Older `.writ/retros/*.json` snapshots and `trends.json` from the git-metrics retro are left in place and no longer written.

**Privacy guard.** Store transcript paths and short factual quotes only: an error message, a command, a user correction in a few words. Never store transcript bodies, prompts, or chain-of-thought. Redact secrets, tokens, and personal data if a quote would contain them.

## Error Handling

| Situation | Response |
|---|---|
| No transcripts found | Print the locations searched and offer `--session <path>` |
| Unknown transcript format | Skip that file, name it in the retro file, continue |
| Scope has no recorded commits or dates | Ask for `--since` or `--session` instead |
| No findings | Write the retro file with zero findings; that is a valid result |
| Proof check does not fail on the mistake | Restore the edited file, set `result passes`, and record `issue` |
| Proof cannot run | Set `result pending` and record `issue`; the issue draft carries the proof command as its done check |
| Rule table malformed, for example by a hand edit | Read it as is. Put the `retro-check.py` reason lines in the final report and leave rows this run did not add or replace unchanged |

## Integration with Writ

| Command | Relationship |

| `/writ:implement-story`, `/writ:implement-spec`, `/writ:implement-phase` | The runs this command reviews |

| `/writ:create-issue` | Receives findings that need design work or a source or test edit |

## Completion

This command succeeds when `.writ/retros/YYYY-MM-DD-<scope>.md` lists every transcript read and every finding with its evidence and disposition, and no source, test, or Writ command file was edited.

**Terminal constraint:** This command proposes and applies environment changes only. Do not edit source code or tests, do not run `/writ:refresh-command` without the user choosing that route, and do not commit.
